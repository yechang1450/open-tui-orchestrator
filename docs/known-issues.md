# 已知问题与已知限制

本表把散落在安全审计、适配器文档、发行策略与验证记录里的已知问题收在一处。
每条都给出**仓内出处**（`路径:行号`），出处那句话就是这条记录的依据；没有仓内出处的说法不收（见文末「未收录」）。

**状态口径**

| 状态 | 含义 |
|---|---|
| 未修 | 已知未处置，当前版本仍在 |
| 已缓 | 有缓解措施（放宽超时、加校验、加告警等），根因未除 |
| 不修 | 按设计保留的边界或定位，不再处理 |

安全类条目的共同前提：本机单用户工具，输入来自本地调用方，窗内 agent 以用户全权限运行（`docs/security-audit-2026-09-09.md:5`）。这些条目不构成跨用户攻击面。

## 未收录（无仓内出处）

以下说法在别处听过或在推断里成立，但仓内找不到可引用的一句话，按本表规则不收：

| 说法 | 为什么不收 |
|---|---|
| 「编排器不支持 Linux / macOS」 | 仓内没有平台支持矩阵；只在 `docs/release-policy.md:78` 提到 MSYS/POSIX 路径语义改由可注入平台的纯函数判定，属测试处理，推不出平台支持结论。 |
| 「Kimi 新版本已提供 hooks 通道」 | 仓内只记录 0.42.0 没有 hooks（`docs/kimi-integration.md:4`）；更新版本的结论无仓内出处。 |
| 「窗口尸体残留是现存问题」 | `docs/release-policy.md:76` 记录为已修复，并带判据 `test/leftover-windows.test.mjs`；属已修项，不进本表。 |

## 维护口径

- 新增条目前先打开来源文件确认那句话还在；行号漂移就改行号，不删出处。
- 修复后不要直接删行：状态改为 `不修` 并补一句"已在某版本修复"会污染表格语义，正确做法是把该行移出本表、在对应文档里记账。
- 安全类条目的前提（同用户/窗内 agent）如果变化，整表需要重新评估，不能只改单行。
